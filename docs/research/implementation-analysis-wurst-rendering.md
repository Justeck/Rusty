## Shared chunk-search architecture and practical improvements

The fully read worker stores a live chunk reference and query, scans x/y/z through the highest nonempty section plus one layer, checks an interruption flag and retains all matches in a list. Coordinator restarts searches on recognized chunk/block/section update packets, range changes or dimension object changes; target-filter change clears all workers. This establishes received-state incremental invalidation, not immutable snapshots or a guaranteed frame/memory budget.

Independent native indexing should snapshot only needed palette/section facts, cap queued/running work and retained matches, tag every result with world/session/filter/chunk revision, and apply it only if those revisions still agree. A low-priority thread pool does not cap CPU, allocation or result sorting. Cancelled tasks may still run briefly; a stale-result check remains necessary. Bound aggregate geometry across Search, CaveFinder, PortalESP, StorageESP and LightOverlay rather than multiplying a per-feature cap by every enabled scanner.

MobSpawnESP's optional slow hitbox mode synchronizes its own helper, while the underlying live-world collision method is explicitly not thread-safe. Synchronizing this helper does not synchronize unrelated world mutation on the game thread. Native code should make collision queries on the owning thread or read immutable geometry, never assume a private mutex makes a global game scene safe.

NewChunks requires exact initial-versus-update observation provenance. Its sets reset on world change and otherwise grow for a session; a native implementation should add finite retention/eviction and display incomplete history. Fluid/palette heuristics can be affected by custom generation, data packs, edited terrain and server transformation, so store the evidence rather than converting it into an unqualified creation timestamp.
