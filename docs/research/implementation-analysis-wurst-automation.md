# Wurst's distinct building, farming and inventory automation

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

The complete bodies of the 18 module classes below were read on 2026-11-04 at Wurst `4e4a957e87ffd79d120835fb47fa9c139006abb8`. AutoBuildTemplate and AutoFarmPlantType/Manager were also read completely. The 21 concrete plant-type bodies, shared BlockPlacer/BlockBreaker/InteractionSimulator internals, AutoFish rod/spot helpers, Wurst pathfinding and several setting/filter helpers are not fully traced in this review. TreeBot's nested tree/angle search subclasses and path processor wrapper were read; its underlying shared A* remains a dependency. No reference code was copied into the native implementation. This is behavioral source review, not reference runtime verification or native delivery.

## Concrete reusable hooks and independence

The high-value native families are crop readiness/replant preview, ordinary hoe/bonemeal/feed interaction sequencing, blueprint placement preview, merchant trade inspection, component-aware restocking and tree-to-vantage navigation. They share an observation/action pipeline without becoming the same feature: each supplies a distinct eligibility predicate, ordering policy, expected acknowledgment and failure reason.

Horizon already has ordinary item/block/entity use, native tool/food components and a bounded path planner; those are the appropriate mechanics to reuse. Never call an actual use handler to predict whether it would succeed, because it can consume items, invoke mod callbacks or change the world. Observation and prediction helpers must remain immutable; the separately owned ordinary action is the only mutation stage.

AutoBuildTemplate's versions accept relative coordinate arrays (v1) or relative position plus block name (v2); its ordered set stores records containing arrays, so value deduplication cannot be assumed from the record/set type. A native schema should explicitly reject conflicting duplicate positions, cap count/extents and store a requested block state rather than assuming block item uniquely determines orientation/state. The source loader's synchronous file parse is not evidence it meets a render/frame budget.

AutoLibrarian's nearest-lectern association is a heuristic. Its optional first-trade purchase does not verify success before saying done, and reading one enchantment entry is not a complete mixed-enchantment policy. An independent task needs a resulting XP/offer lock acknowledgment and stop conditions for missing profession updates. These are material limitations of feature parity, not reasons to invent inaccessible villager data.
