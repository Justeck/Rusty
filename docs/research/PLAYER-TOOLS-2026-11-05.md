# Further player-tool research and native Rust designs

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

Reviewed 2026-11-05. This supplements the earlier reference-client analysis. It does **not** add modules to Rusty 1.2, change its accepted executable, or claim that a reference mod has been run. The current product has 42 modules; the proposals below are distinct from that delivered catalog. [Source identities and review scopes](player-tools-2026-11-05.json) record 10 projects and 28 primary source files, including seven selected implementation files. Their transitive dependencies and complete behavior were not exhaustively traced.

## Findings that change implementation choices

Useful advantages include less time finding materials, fewer accidental inventory changes, clearer environmental information and steadier rendering. Combining everything into one always-running scan would work against those benefits. The recommended direction is to extend the existing Rust tools and their shared workload limits, with new modules only when the interaction has a separate purpose.

Some reference features depend on data a normal remote client lacks. Jade separates client tooltips from explicit server-data providers. AppleSkin's documented extra synchronization cannot establish that exhaustion is available from an arbitrary server. Recipe data, unopened container contents, unknown chunks and server health rules also have independent availability boundaries. Represent an observation as **received**, **calculated from received facts**, **estimated**, or **unavailable**. A plausible number must not silently become a received fact.

This is an original design proposal, not a promise of equal behavior across games or servers. The sources' default branches include older Minecraft targets. Those pinned identities are research references, not claims of current 26.3 compatibility.

## Shared architecture and efficiency rules

Keep the runtime and native adapters in Rust. Retain Python for development orchestration where it already drives useful game checks; rewriting test coordination does not improve frame time. Packaging is already available through the optional Rust release tool. Adding Java mods as dependencies would not supply their behavior to Horizon.

Use small pure observation models with explicit availability and provenance. Native adapters read the appropriate received state and produce immutable bounded snapshots. Rendering consumes those snapshots without inventory actions, blocking file reads or full-world scans. Group resource, world/session, dimension, registry and configuration generations separately; a change in one should invalidate the data it actually owns.

Any future worker should receive owned snapshots, not pointers or references into live mutable game state. Drop results from an old generation. Bound the work queue, retained snapshots, results and GPU resources; expose partial progress instead of falling back to an unbounded loop. Keep GPU creation/destruction on the supported render path. Rust prevents many lifetime mistakes but does not make an unbounded cache or retained `Arc` cheap.

Existing action ownership remains authoritative. A user gesture creates finite intent, a server correction is a received fact, and a predicted click is neither acknowledgment nor permission for endless retries. Cancellation on menus, focus loss, manual input and world changes must be shared across action modules. Passive previews should never acquire action ownership.

The proposed rollout is: diagnostics and controlled memory attribution; passive alerts/details/material lists; deliberate inventory helpers; recipe/blueprint systems after separate designs. This orders work by player benefit and verification cost. It is the author's recommendation, not a claim that the user approved each specific new design.

## Performance and correctness release gates

1. Establish exact source, package, stage and executable identities for the candidate. New runtime code requires a new package/build and affected game tests; old 1.2 evidence cannot validate it.
2. Pure Rust tests cover unknown values, finite limits, arithmetic overflow, generation resets and action state transitions. Native checks prove the adapter compiles against the pinned API.
3. Actual game fixtures cover received updates, unloading, disconnect/rejoin, two worlds and dimension transitions. Inventory/action behavior needs a separate owned Survival server with authoritative readbacks, including rejection/correction cases.
4. Review original captures at normal and extreme menu/HUD sizes. Test help, resets and cancellation, not just the presence of a toggle.
5. Measure matched enabled/disabled workloads on the same candidate. Record warmup, caps, resolution, queues, CPU/GPU frame times and allocation/resource counts. Other projects' Java benchmarks are not Rusty measurements.
6. Investigate the observed 1.2 memory growth with repeated world-transition cycles, fresh disabled controls and allocation/resource attribution before calling it a Rusty leak or claiming a fix. Include longer idle and multi-hour runs when feasible.
7. Publish only accepted capabilities, preserve license notices and immutable existing releases, then install the exact public revision through Horizon and verify supported Build and Play.

Server-side anti-X-ray, undisclosed inventory contents, remote simulation authority and unloaded terrain remain boundaries. No proposed feature relies on obtaining deliberately withheld data, altering server authority or loading Java loader code inside Horizon.
