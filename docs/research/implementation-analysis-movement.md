# Movement behavior review and native navigation reuse

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

Read 2026-11-04 against Meteor `e3a2e77967629d216e127b5ceecf71fb15f9d2e5`. All 29 top-level movement module bodies were read, followed by the nested Speed and ElytraFly module bodies and every one of their mode/base classes. This covers 31 movement modules, not every client's movement module. Settings identifiers are retained in the register; method review does not mean all transitive helper/mixin implementations or reference runtime behavior were verified. No native delivery or server compatibility is awarded here.

The source link for every row is the pinned [movement directory](https://github.com/MeteorDevelopment/meteor-client/tree/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/movement) plus `<Module>.java`; the machine register contains each complete URL and exact methods/lines. Each row below identifies a distinct mechanism rather than treating all movement names as one feature.

## Nested Speed and ElytraFly mode families

The full [Speed](https://github.com/MeteorDevelopment/meteor-client/tree/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/movement/speed) and [ElytraFly](https://github.com/MeteorDevelopment/meteor-client/tree/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/movement/elytrafly) subtrees were read, including all six concrete mode classes and both base classes.

Common source pitfalls matter for original designs: ElytraFly computes destination chunk with truncating integer conversion rather than floor, which is wrong around negative chunk coordinates. Takeoff/replacement and chest-restore paths need successful item search, exact ownership and session invalidation. Ground/instant-drop listeners can remain subscribed after the main module deactivates; all deferred work needs generation cancellation on world leave. Source restore writes are not sufficient evidence that a prior user setting was preserved.

## Credible fall-protection mechanism in more detail

Meteor NoFall's Place mode is substantially more careful than a generic ground-claim rewrite. Its eight-tick landing simulation integrates current acceleration, gravity, friction and collision without moving the real player. When the bounding box reaches a landing, it tests the center and four foot corners to identify an upward support face. Before using the item it checks the current world/mode, recomputes landing, traces reach again and ensures the player is still falling. Water-evaporating environments choose powder snow when configured water would be unsuitable. Collection waits for the placement sequence to be acknowledged and at least two settled ticks. Pickup acknowledgement and a ping-scaled timeout prevent a rejected local prediction from permanently blocking future protection. This is source behavior, not a measured success rate.

An original Horizon implementation can reuse normal bucket/block use, block-update acknowledgements and collision simulation, while starting with a warning/landing preview until those actions are validated. Native geometry and simulation order must match the pinned host, and server state can still defeat a last-moment rescue. A proposal needs finite item-use retry limits and a generation token; a delayed callback may not run after world/menu changes. Compare confirmed player health and world blocks, not just an animation or sent packet.

## Native planner already available

Pinned Horizon `crates/horizon-client/src/game/agent_navigation.rs` already implements `find_path`, `Plan::aim`, `arrived` and `Progress`. It uses a priority heap plus cost/predecessor maps, four horizontal neighbors and level/up-one/down-one-to-three candidates, with clearance checks. Unknown cells block movement, lava is excluded, water is more costly and supplied failed edges are avoided. A 30,000-expansion limit can return a closer partial frontier. `Plan.complete` distinguishes that from arrival; consumed partial plans do not aim at an unknown final goal. Progress measures new best horizontal improvement so jumping or oscillating does not indefinitely reset stuck detection. Source tests cover these exact cases but were not run in this research task.

This is a useful MIT host component, not a Baritone dependency. It has limitations: coarse solid/fluid cells do not fully represent arbitrary voxel shapes, the search is synchronous, and the Manhattan heuristic can overestimate the cost of a combined horizontal/vertical move, so shortest-path optimality is not established. The hard node cap is not a millisecond frame budget. A practical first native waypoint path preview should cap distance/search time, use received geometry, mark partial routes, replan on revision changes and stop before any unknown edge. A route executor additionally needs input ownership, collision-accurate movement and real local/multiplayer correction tests.

`game/agent.rs` integrates normal `goto`, `break`, `place`, `use-item`, look and selection tasks advanced over frames with timeouts. Its task logic is a candidate for internal reuse; a player module should not open or depend on an external control socket merely to navigate. Read the relevant task-body and cancellation behavior before reuse. The root project can adapt these host methods inside the correct mixin scope instead of introducing a second unrelated pathfinder.
