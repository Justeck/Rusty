# Meteor commands: individual mechanisms and native boundaries

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

All 39 command bodies were read completely on 2026-11-04 at `e3a2e77967629d216e127b5ceecf71fb15f9d2e5`, including Locate, Server, Swarm, Nbt and Notebot. Primary evidence: [pinned command sources](https://github.com/MeteorDevelopment/meteor-client/tree/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/commands/commands). Brigadier supplies typed grammar/suggestions but does not itself establish permission, session ownership or actual server acceptance. Referenced profile/Starscript/argument/parser/render/network helpers remain separate review boundaries except where another analysis explicitly traces them. No reference code was copied or executed.

Native adaptation should expose typed original actions over Rusty's actual registry and ordinary host operations. Display-only features may be local; gameplay changes require normal host semantics and received confirmation. Optional files/network services need bounded parsing, thread-safe UI handoff, timeout, cancellation and a current-session check. Every entry has a distinguishing acceptance requirement below.

These39 rows close command **entry-body reading**, not full transitive compiler/parser/network/helper review, reference runtime testing or native implementation acceptance. The source algorithms that are meaningful to adapt are bounded task scheduling, exact typed setting controls, map/component inspection and uncertainty-aware observed triangulation; packet/state fabrication is not evidence of an ability the native server supports.
