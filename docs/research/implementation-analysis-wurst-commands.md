# Wurst command behavior, authority and practical equivalents

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

All 52 command bodies were read completely on 2026-11-04 at `4e4a957e87ffd79d120835fb47fa9c139006abb8`. Evidence: [pinned command directory](https://github.com/Wurst-Imperium/Wurst7/tree/4e4a957e87ffd79d120835fb47fa9c139006abb8/src/main/java/net/wurstclient/commands). Repeated pagination/profile/settings patterns are grouped architecturally below, but every command has an individual behavior and verification row. A command delegating to a helper is not credited with a full helper audit. Registry settings/classes/hashes remain in the machine-readable register. Reference code was neither copied nor executed.

Native commands should be structured actions using stable feature IDs and typed arguments, with exact arity, finite/range checks, explicit authority and session checks before mutation. Local preview, action request and received result are different statuses. Profile imports need size/depth/schema/path validation and atomic application; source wrappers merely appending `.json` do not establish containment. Bulk destructive operations require a concrete reviewed set and recovery mechanism. Repeated command invocation must not create duplicate listeners/actions.

Command convenience is not a separate source of gameplay authority. The strongest practical equivalents are precise typed controls over already implemented features, normal navigation, lossless received-data inspection and safe profile workflows; creative edits remain permissioned and require server-confirmed outcomes.
