# Wurst combat, targeting and follow-controller differences

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

Complete module bodies below and the complete AttackSpeedSliderSetting were read on 2026-11-04 against Wurst `4e4a957e87ffd79d120835fb47fa9c139006abb8`. These are 18 additional module reviews; AutoSword, AutoPotion and AutoSoup are in the automation supplement, and TriggerBot in the main analysis. Shared entity attackability/filter implementations, normal game action internals, rotation helpers, pathfinding base classes and several inventory helpers are not all traced. This review does not copy source code, execute reference clients, verify server acceptance or award native implementation.

Primary source: [Wurst hacks directory](https://github.com/Wurst-Imperium/Wurst7/tree/4e4a957e87ffd79d120835fb47fa9c139006abb8/src/main/java/net/wurstclient/hacks); exact individual pinned URLs and setting/method navigation are retained in [the register](implementation-analysis-register.json).

## Shared timing, rotation and ownership findings

The full [AttackSpeedSliderSetting](https://github.com/Wurst-Imperium/Wurst7/blob/4e4a957e87ffd79d120835fb47fa9c139006abb8/src/main/java/net/wurstclient/settings/AttackSpeedSliderSetting.java) uses an integer millisecond-like countdown decremented by a fixed amount per update. Automatic mode separately checks actual attack recharge. Optional random offset is Gaussian, so its setting is a scale rather than a strict ±maximum bound. Several modules call update/reset from different event stages. Native code should state tick versus monotonic-time semantics, clamp deadlines, avoid action catch-up bursts and test actual cooldown after an equipment change. Timing variation does not establish compatibility with another server implementation.

Most source modules disable many peers on activation. Independent native architecture should preserve user preferences and arbitrate per-action requests instead. A selected slot can be restored only if the same owner still controls it, the stack/session matches and the user has not scrolled. A target selected during update must be revalidated at attack time for identity/alive/range/LOS/relation, even if the rendering marker is still valid.

Static source observations with concrete independent tests:

- Killaura/AimAssist select a winner before optional LOS and then clear it when blocked, rather than selecting the next visible candidate. Native eligibility must precede ranking.
- AnchorAura disables itself on a dimension where anchors function normally, but the current update continues without returning. Native disallowed state must exit before preparing any action.
- Protect constructs an entity pathfinder before checking that nearest protected entity exists; the constructor dereferences it. An empty world must be a clean no-target state.
- Follow's invalid-target branch includes a null case, but its reacquisition predicate dereferences the previous entity for a name. Store stable optional identity separately and never read a cleared target.
- Synthetic movement, direct relocation and local fall-state changes remain different mechanisms from ordinary action assistance. Their existence in reference code does not justify claiming portable accepted flight, reach, critical or damage results.

These are body-level findings and native design requirements. They are not runtime reproductions, reference benchmarks, server compatibility guarantees or permission to mutate gameplay during research.
