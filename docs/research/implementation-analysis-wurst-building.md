## TemplateTool delegated algorithm follow-up

Complete additional reads: `TemplateToolState`, `SelectPositionState`, `SelectBoxStartState`, `SelectBoxEndState`, `SelectOriginState`, `ScanningAreaState`, `CreatingTemplateState`, `ChooseNameState` including nested screen, and `SavingFileState`. Primary evidence is [the pinned state directory](https://github.com/Wurst-Imperium/Wurst7/tree/4e4a957e87ffd79d120835fb47fa9c139006abb8/src/main/java/net/wurstclient/hacks/templatetool).

Selection holds normal use to choose the crosshair block; sneak chooses its adjacent outside cell. Enter advances once there is a stored selection. There is no press-edge debounce, so held Enter can progress subsequent selection states if their values are already present. Start/end capture an inclusive box; scan computes unchecked integer axis lengths/product and processes `clamp(volume/30,1,1024)` cells per tick, retaining nonreplaceable state snapshots in insertion order. It does not establish received-chunk validity or freeze a world revision. A per-tick scan limit does not bound retained total memory or make an overflowed volume valid.

Creation builds a distance-to-origin ordered set with position tie-break. The first entry is nearest to the chosen origin, which may be outside the captured set. Each subsequent step scans all remaining entries and prefers the closest to the last output block among entries touching any prior output block. When none touches, it falls back to the first remaining entry. This is a greedy connectivity heuristic, not a support/survival/dependency solver or shortest traversal. A nominal cap on outputs per update still permits quadratic total neighbor/distance work. Progress changes its meaning after the initial set-building phase and uses remaining fraction during ordering.

Export translates coordinates relative to origin, projects horizontal displacement onto cardinal left/front, and preserves vertical displacement. The cardinal frame is read from player facing **when saving**, rather than fixed at capture. Version1 stores positions only; version2 stores block registry names with positions. It discards orientation, waterlogging, shape state, block entity content and item metadata. Full-state reconstruction cannot be claimed from this file format. The name screen allows32characters and resolves `name + .json` against a folder, but does not verify normalized containment. Existing file warning is informational; save uses direct overwrite, default-encoding FileWriter and no atomic replacement.

An independent future native capture/export should reject oversized/unreceived selections before scanning, freeze session/world revision plus explicit orientation, preserve exactly the state fields the original schema promises, and bound work by **examined edges**, not only outputs. Placement order needs support dependencies and cycle/disconnected reasons. Save should use a validated contained path, UTF-8, explicit existing-file handling and atomic write. Discriminating tests: reversed/integer-limit corners, empty region, world edit between scan slices, unknown chunks, disconnected floating islands, gravity/tall/attached blocks, duplicate states, outside origin, rotating before save, traversal/symlink destination and interrupted write. Current native Build Planner does not implement capture/template import and makes no such claim.

## Shared geometry/action requirements

The complete shared Nuker settings distinguish shape, flat floor, clicked ID/locked ID, multiple-ID allowlist and instant-break filter. Those are not synonyms: a cube may contain corners beyond actual reach, flat mode depends on player's current Y, and a clicked ID can change midway through a task. Snapshot intended region/filter at task start or make edits explicitly invalidate the queue.

All build/mining equivalents should separate eligibility proposal from actual normal action and received completion. A proposal captures world/session/chunk revision, exact block state/shape, supporting face, material components/count, actual reach/LOS and required posture. Revalidate before action, wait for host acknowledgment, then update progress; retry count/time and retained plan size are finite. No local remove, attempted use or cached recent-break marker proves the server changed a block.

Tunneller's task decomposition is valuable, but direct key clearing and per-tick disabling of peers would erase user intent. Preserve physical input and suspend competing requests instead. A falling-block wait needs timeout and a liquid retreat must validate the route rather than moving into unknown cells. Cleanup must release movement/mining/rotation/slot leases even if the task exits before the next gameplay tick.
