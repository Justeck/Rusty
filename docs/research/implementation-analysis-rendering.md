# Rendering, camera and received-state algorithms

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

All 38 Meteor Render module bodies (including nested BlockESP and Marker directories) were read on 2026-11-04 at `e3a2e77967629d216e127b5ceecf71fb15f9d2e5`. Review covers constructor-through-end module methods plus the entire projectile simulator. Many getters depend on additional rendering mixins that are not all traced here; shader implementations, model helpers and full waypoint persistence helpers remain separate dependencies. Setting identifiers and per-file pinned primary URLs are retained in [the register](implementation-analysis-register.json). This is source analysis, not reference execution or native acceptance.

Primary directory: [Meteor Render](https://github.com/MeteorDevelopment/meteor-client/tree/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/render).

## Projectile simulation details

The complete [ProjectileEntitySimulator](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/utils/entity/simulator/ProjectileEntitySimulator.java) was read. It distinguishes launch speed/gravity/air/water drag and tick-order by projectile family. Throwables use gravity then drag then position; arrows use position then drag then gravity; fishing/firework handling uses gravity then position then drag. Bow charge, crossbow charged-projectile component/piercing, shooter known movement, crouched eye height and server rotation affect launch. Fishing bobber has its own launch calculation.

Each step checks water intersection against projectile bounds/fluid height, stops below world or at unloaded chunks, and sweeps from previous to current point so the initial segment cannot skip a wall. Block collision shortens the segment before entity tests. Arrows can collect multiple piercing hits, the first self hit is ignored and deflection handles shields/Breeze/world border approximately. Moving target future occupancy is not fully modeled. Some stationary velocity normalization/zero-dimension edge cases need independent handling rather than trusting every source branch.

An original Horizon implementation should derive constants/order from the host projectile code, use stable item/resource revisions and cap total predictions/rays. A gravity-only parabola is a useful labeled preview for a declared projectile subset; it cannot claim the bow/crossbow/fishing/potion/deflection precision just described. Drawing a path also does not implement BowAimbot's interception/rotation policy or ArrowDodge's movement selection. Compare predicted points against received actual trajectories in the same controlled world, including water and moving-shooter cases, before an accuracy claim.
