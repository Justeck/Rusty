## Shared action architecture

The recurring difficulty is interaction ownership rather than translating a Java module class. Movement, eating, attacking, building and selecting equipment compete for the same controls and player state. A native implementation should resolve per-tick action requests before mutating normal host input. A lease records owner, session generation, target identity, selected-slot before/after and expiration. Manual input, a changed screen, death, disconnect, dimension change, invalid target or server correction cancels the lease. Restore a selected slot only if it still equals the module's chosen slot and the original session remains active. Releasing an automatic request must preserve a physically held key.

Do not imitate reference implementations that disable and later re-enable other modules to obtain temporary control: a user may intentionally disable a paused module in the meantime. Suspend requests while preserving preferences. Inventory mutation needs a serial queue bound to menu identity and revision, carried-stack preconditions and acknowledgement or resynchronization. One ordinary action per validated step is preferable to many speculative clicks with a delay between them. Rotations need the same ownership and expiration rules. Timers use simulation ticks for gameplay and monotonic time for UI timeouts; do not replay a burst after a long frame.

Pinned Horizon `game.rs` exposes the relevant normal behavior within the game implementation: `use_item` / `use_item_as_player` around lines 6200/6204; `inventory_quick_move` around 9403; `attack_strength_scale` around 11530; `attack` around 11677. Hotbar selection is `self.selected`, loaded from `level.selected_slot` around 12251 and persisted around 15138. These methods are private: source mixins must enter the correct implementation scope and exact pinned source must be rechecked. Their presence is not a public SDK guarantee. Use normal host actions rather than inventing packets or locally crediting unconfirmed results.

## AutoTool and durability protection

**Read:** Meteor `player/AutoTool.java` complete body; Wurst `AutoToolHack.java` complete body. Wurst chooses an actually faster hotbar tool, adds the efficiency contribution to mining speed, optionally excludes swords, protects tools at an absolute remaining-use threshold, supports a hand fallback, and remembers a previous selection. Meteor filters tools by valid drops and per-item allow/deny lists, ranks destruction speed ahead of enchantment preferences, supports Silk Touch for ender chests and Fortune for ores/crops, and adds a configurable switch delay plus percentage-based protection. Its mining handler and tick handler are separate; InfinityMiner suppresses normal AutoTool.

**Native choice:** score the current registry/component-derived speed and drop suitability for the exact targeted block; use configurable enchantment preference as an explicit tie policy. Prefer the current slot for ties. Scan at most nine hotbar slots on target/item change, not the whole inventory per frame. Check durability only for damageable stacks; unknown component data must not be treated as a healthy tool. A first delivery can select an eligible hotbar slot without moving items. Full-inventory search is a separate inventory-transaction capability. Return on mining end only under ownership rules above.

**Why:** item-name suffixes cannot model custom data packs, effective block sets, shears, component overrides or enchanted speed. Neither reference scoring heuristic proves optimal drops or minimum break time for all states. Wurst's damaged-tool fallback includes inventory movement, so that mode cannot be represented as mere hotbar selection. An apparent comment/predicate mismatch exists in its empty-slot search; do not reproduce it. Test slow/fast equal-score tools, missing suitable tool, threshold exactly reached, unbreakable stack, custom tool component, creative mode, target switch during delay, manual scroll and cancelled mining. Ordinary server mining speed remains authoritative.

Sources: [Meteor AutoTool](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/player/AutoTool.java), [Wurst AutoTool](https://github.com/Wurst-Imperium/Wurst7/blob/4e4a957e87ffd79d120835fb47fa9c139006abb8/src/main/java/net/wurstclient/hacks/AutoToolHack.java). RusherHack additionally documents attack/shield use, tool-return, inventory scope and durability preference, but its ranking internals are unavailable: [official AutoTool](https://rusherhack.org/features/modules/AutoTool.html).

## AutoEat, AutoGap and healing

**Read:** Meteor `player/AutoEat.java` complete body. It exposes health/hunger/OR/AND triggers, food priority by nutrition/saturation/combined, a food blacklist, optional inventory search and temporary pauses for combat/pathing. Defaults exclude several harmful or valuable foods. Candidate selection prefers edible offhand, then hotbar, then optional main inventory. Main-inventory food requires an empty hotbar destination. It prevents ordinary targeted-block interaction while eating. It releases its use state and restores selection when stopping. Eligibility requires a food component and either hunger room or an always-edible food. Health alone does not make ordinary food usable at full hunger.

**Native choice:** begin with hotbar/offhand only; expose hunger threshold, allowed food policy, keep valuable/teleporting/harmful food excluded by default, and preserve the user slot. An independent finish policy can complete the current bite and then reevaluate thresholds, avoiding oscillation when another effect changes hunger mid-use. `Until full` is distinct from `finish this item`; show both meanings if both exist. Use ordinary item-use semantics while ensuring a chest, villager or entity under the crosshair does not receive the automatic use. A hunger-only first implementation must not claim AutoGap or potion healing.

**Risks and tests:** normal `use_item_as_player` tries entity and block interactions before generic item use, so blindly calling it can open a container instead of eating. Do not simulate global mouse clicks. Test full hunger/low health, always-edible food, depletion mid-bite, selected offhand, no eligible food, manual scrolling, screen opening, user-held use, death and a delayed/rejected use. Check item count/hunger after the host update; a request is not a completed consumption.

Sources: [Meteor AutoEat](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/player/AutoEat.java). RusherHack documents separate finish and until-full policies and optional special-food conditions; these are configuration evidence, not observed internal selection logic: [official AutoEat](https://rusherhack.org/features/modules/AutoEat.html).

## SafeWalk, edge sneaking and Parkour

**Read:** Meteor `movement/SafeWalk.java`, `movement/Parkour.java` and Wurst `SafeWalkHack.java` complete bodies. Both SafeWalk implementations inspect a contracted/extended player collision box beneath the feet; visible sneaking is optional. Meteor additionally estimates expected fall distance using a height map or downward collision ray. It can fall back to normal ledge clipping when sneaking is not sufficient. Wurst disables Parkour on activation. Meteor Parkour checks grounded state, user jump and sneak, tests a shrunken downward box for support, then invokes a normal ground jump.

**Native choice:** normal edge clipping or an ordinary sneak request driven by the predicted next horizontal footprint and real collision shapes. Sampling only the center block misses diagonal edges, slabs and narrow shapes. Cap prediction distance, preserve physical sneak, and distinguish unknown terrain from proven support. An edge jump is a separate mutually exclusive action policy; user sneak should always allow deliberate caution and suppress Parkour. Ground-jump assistance must not be labeled flight or NoFall.

**Tests:** one-block ledge in all eight horizontal directions, diagonal sprint, top/bottom slab, stairs, carpet, fence, trapdoor, ice, liquid, moving platforms/vehicles if supported, knockback, loss of focus, overlay opening and world transition. Server correction cancels predictions; the client cannot guarantee avoiding all falls. RusherHack's official settings name slabs and riding, supporting useful separate test scopes without revealing its collision algorithm: [Safewalk](https://rusherhack.org/features/modules/Safewalk.html).

Sources: [Meteor SafeWalk](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/movement/SafeWalk.java), [Meteor Parkour](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/movement/Parkour.java), [Wurst SafeWalk](https://github.com/Wurst-Imperium/Wurst7/blob/4e4a957e87ffd79d120835fb47fa9c139006abb8/src/main/java/net/wurstclient/hacks/SafeWalkHack.java).

## TriggerBot, Aura and targeting

**Read:** Wurst `TriggerBotHack.java` complete body; Meteor `combat/KillAura.java` target/timing/action bodies. TriggerBot operates only on the current entity hit result, validates attackability, hitbox distance and entity filters, optionally switches weapon, and schedules attacks through an attack-speed timer. Its simulated mouse option explicitly warns of accidental menu clicks. KillAura constructs a filtered target list, validates entity life, mode, type, reach, visibility, tame status, friends and weapon, supports shield-breaking selection, pauses for lag/use/pathing, optionally owns rotations, and gates actions on vanilla charge or a custom delay. These are substantially different feature scopes.

**Native choice:** first implement a crosshair-only, cooldown-respecting ordinary attack. Use the host raycast, current reach and normal attack method; do not increase reach merely because a reference permits a larger setting. Revalidate target identity and occlusion immediately before dispatch. Filter players, friends, tamed/passive/named entities explicitly; missing relationship data should be visible. An Aura requires a bounded candidate index, deterministic ranking, line-of-sight tests, yaw/pitch rate limits and shared rotation ownership. Avoid scanning every entity multiple times per frame.

**Tests:** target crossing a wall, item frame/painting closer than mob, friendly entity, spectator/creative target, target death/despawn, player death, attack charge after a weapon switch, using food/shield, menu/focus/freecam and server rejection. Horizon `attack()` handles several special targets before normal mobs; restricting the trigger candidate first prevents unintended hits on those objects. Reference anti-cheat descriptions and advertised critical-hit guarantees are not transferable acceptance evidence.

Sources: [Wurst TriggerBot](https://github.com/Wurst-Imperium/Wurst7/blob/4e4a957e87ffd79d120835fb47fa9c139006abb8/src/main/java/net/wurstclient/hacks/TriggerBotHack.java), [Meteor KillAura](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/combat/KillAura.java). Official proprietary scope: [RusherHack TriggerBot](https://rusherhack.org/features/modules/TriggerBot.html), [Future Combat list](https://futureclient.net/).

## Scaffold, placement previews and building pipelines

**Read:** Meteor `movement/Scaffold.java` complete body. It predicts a position beneath the player using movement, optionally offsets ahead from input/yaw, adjusts descending height, searches nearby positions with a valid placement side when needed, filters hotbar blocks by shape and falling-block stability, and delegates placement through shared helpers. Air-place mode builds a bounded-radius list, sorts by distance, and enforces a blocks-per-tick setting. Fast tower changes velocity; that is a separate server-sensitive mode, not normal bridge placement.

**Native choice:** share a placement planner between a visible preview and execution. A proposal records target cell, supporting face, hit position, selected material, reach, collision, session and geometry revision. Confirm all preconditions again before one ordinary placement. Replan after acknowledgement or rejection. Never color an attempted placement as a confirmed block. Preview only is useful while action hooks are being validated. Start with adjacent supported full-block placement and a finite cell budget; expand to schematic/line/wall plans through the same queue. Keep a material count and an explicit blocked/unknown reason.

**Performance:** Meteor's fallback searches a volume and sorts candidates each tick. Native code can enumerate a small nearest-first neighborhood and keep the best admissible candidate without materializing/sorting all positions. Unknown chunks, replaced supports, partial blocks and entity collision must invalidate the plan. Test materials exhausted, falling blocks, occupied targets, world height/border, a container support, diagonal movement, latency, permission denial, user cancellation and reconnect. No local velocity tweak establishes server-authorized tower/flight.

Sources: [Meteor Scaffold](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/movement/Scaffold.java). RusherHack documents block filters, delay, safewalk, support-ray/rotation controls and render depth; closed-source placement timing remains unknown: [official Scaffold](https://rusherhack.org/features/modules/Scaffold.html).

## Hotbar replenishment and protected inventory

**Read:** Meteor `player/AutoReplenish.java` complete body. It snapshots ten slots, refreshes snapshots after closing a screen, requires the normal player menu, compares low-stack or newly emptied slots, can include offhand and unstackables, compares item/components for merging and optionally enchantments for replacements, excludes selected/offhand sources, and prevents certain hotbar-to-hotbar loops. AutoTotem's offhand lock prevents competing replenishment.

**Native choice:** bind a desired-slot template to component identity and a protected-slot policy. Plan one transfer from an eligible source, preserve cursor state, and wait for the normal inventory revision before planning another. Preserve hotbar roles even when a stack reaches zero by remembering the last confirmed eligible item. Do not infer a refill request from every empty slot. Handle components, renamed stacks, maximum stack size and non-stackable replacement separately. Avoid moving a currently used or manually selected source.

**Tests:** stack crosses threshold and empties in one tick, equal item with different components, smaller stack limit, full inventory, cursor-held stack, open chest, totem consumption, slot edit by user, delayed revision, server forced-close and reconnect. Delays alone do not prove transaction safety. Future's public changelog describes a failure interaction between fast totem equip and replenishment; this is direct evidence that these modules need shared ownership, not a reason to claim a particular proprietary fix.

Sources: [Meteor AutoReplenish](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/player/AutoReplenish.java), [Future changelog](https://futureclient.net/).

Meteor `combat/AutoTotem.java` was also read completely. Strict mode keeps a totem equipped whenever one exists; Smart mode compares health plus absorption minus estimated possible fall/explosion reductions against a configurable threshold, with a separate elytra-flight condition. It counts inventory totems, exposes an offhand lock to competing modules, delays slot movement and resets its delay after a received death-protection entity event for the local player. Its risk estimate depends on PlayerUtils helpers that are not fully audited here. An independent first native version can implement explicit health/absorption thresholds and always-hold policy using the validated inventory queue, then add separately labeled damage estimates. Test the last totem, an occupied offhand, delayed slot update, totem pop, food/shield ownership, rejected click and server-specific damage. A totem count/alert HUD is useful while mutation is gated, but is not AutoTotem. Source: [Meteor AutoTotem](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/combat/AutoTotem.java).

## Sorting, container transfer, anti-drop and AutoArmor

**Read:** Meteor `misc/InventoryTweaks.java` sorting/transfer/anti-drop bodies; `combat/AutoArmor.java` scoring and application bodies. InventoryTweaks cancels sorting on screen change, processes a sorter over ticks, exposes transfer delays, and filters auto-drop and protected items. Its sorting path may drop a cursor-held stack if no empty slot exists; a native equivalent should instead refuse or return that stack safely. AutoArmor groups eligible equipment by slot, ranks protection/enchantments and armor attributes, protects binding-cursed gear and an optionally retained elytra, prioritizes worn pieces near breakage, and applies paced swaps.

**Native choice:** never run sorting in an arbitrary menu with assumed slot numbers. Use a typed menu/slot layout, preserve carried items and excluded slots, simulate a complete transfer plan before executing it, and abort on any revision divergence. Container transfer should be an explicit take/deposit policy with space estimates; cleaning should first preview candidates rather than discard by vague name matching. Armor ranking should show its actual objective: blast protection, general protection, durability or elytra retention are different preferences. Slot eligibility comes from equippable components, not suffixes.

**Tests:** custom/chest/creative menu, stack component differences, curse of binding, full inventory, cursor occupied, elytra use, protected slots, no better armor, rapid server revisions and user interruption. A read-only armor/durability HUD remains a different capability from AutoArmor. Read-only container components cannot reveal unopened server inventories.

Sources: [Meteor InventoryTweaks](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/misc/InventoryTweaks.java), [Meteor AutoArmor](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/combat/AutoArmor.java).

## AutoFish and observation-driven automation

**Read:** Meteor `player/AutoFish.java` complete body. A three-state machine distinguishes idle, waiting for a bite and waiting to reel. It handles a hooked entity immediately, reads the bobber's caught-fish state, delays reels/casts, scales delays using observed tick rate, and chooses a usable rod by enchantment score with stable selected/hotbar/offhand ties. It optionally avoids a rod on its last durability point. The caught-fish access is provided by a mixin; the module does not merely reel at every splash sound.

**Native choice:** locate the owned bobber by owner/session identity, use only received bite/caught state that the host exposes, and dispatch normal rod use after finite delays. A global splash sound is an ambiguous fallback because other players can fish nearby; if used, require proximity and matching own bobber, label reduced confidence and do not claim equivalent precision. Add a timeout for a missing/unloaded bobber and cancellation on manual rod change. Random delay is not a correctness mechanism or an anti-cheat guarantee. Test two nearby anglers, hooked entity, dry cast, unknown bite state, rod depletion, server lag, unload and dimension change.

Source: [Meteor AutoFish](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/player/AutoFish.java).

## StorageESP and received-world observations

**Read:** Meteor `render/StorageESP.java` color/interact/render bodies. It iterates received block entities, distinguishes storage types, supports box/shader rendering and tracers, uses fill opacity and nearby fading, and records interacted positions including both halves of a double chest. Trapped chests are checked before their superclass. Interaction marks can hide or recolor boxes. A click does not prove successful opening or empty contents.

**Native choice:** reuse bounded received-block scanning and a type filter with per-type color, distance and outline/fill/depth options. Use one snapshot for finder/storage overlays and HUD counts. Incremental updates avoid scanning every cell each frame; a nearest-first capped result set should report truncation. Store interaction marks by world, dimension and block identity with invalidation on replacement; do not infer ownership or loot quality. Test double chests, trapped chests, barrels, shulkers, furnaces/hoppers, minecart storage, replacement, unload, dimensions and a dense storage fixture. Shader geometry and axis-aligned boxes are distinct visual modes requiring separate acceptance.

## Light overlay and spawn-risk honesty

**Read:** Meteor `render/LightOverlay.java` complete body plus `BlockUtils.isValidMobSpawn` / `isValidSpawnBlock`. It scans a configured neighborhood via BlockIterator, reuses pooled crosses, checks empty/single-snow space and a restricted supporting-block predicate, then distinguishes low block light from low sky light. Its helper is an approximation: the body does not test every species, biome, difficulty, distance, structure or server spawning rule.

**Native choice:** call this a light-risk overlay unless the complete spawn predicate is implemented. Read block and sky light separately, retain unknown light as unknown, and render current darkness versus potential nighttime darkness differently. Eligibility needs collision support and space checks; do not mark every dark solid cell. Default to a small volume and incremental scan budget, with cache invalidation on light/block updates and session changes. Test torch removal, skylight/day/night, no-skylight dimensions, stairs/slabs/glass/snow, unknown chunks and fullbright enabled. Fullbright affects display, not authoritative spawn light.

## Trajectories, projectile prediction and BowAim

**Read:** Meteor `render/Trajectories.java` path generation/render bodies; its separate simulator dependency has not been fully audited in this supplement. It chooses main/offhand eligible items, simulates paths, adds crossbow multishot offsets, optionally includes other players and already fired projectiles, and renders collision markers and per-tick boxes. A zero simulation-step setting permits an effectively unbounded loop until the simulator stops. Source comments describe multishot as approximate.

**Native choice:** reuse Horizon's projectile constants and collision functions where available; declare exactly which items/charge/enchantments are modeled. Integrate position/velocity/drag/gravity in the host's tick order, sweep each step against known collision geometry, stop at the first unknown boundary, and enforce both a path cap and global point budget. Label a prediction and uncertainty; a line is not guaranteed impact. Entity motion prediction and server ping widen uncertainty. Recompute on aim/item/charge/geometry changes and amortize other-entity paths. BowAim additionally needs an independently validated interception solver and rotation policy; drawing a ballistic line does not implement an aimbot.

**Tests:** shallow/steep angles, shooter movement, bow charge, crossbow/projectile variants, water drag, block-face grazing, high-speed tunneling, unknown chunks, moving targets and empty/nonfinite inputs. A simple gravity-only curve must be described as an approximation rather than full parity.

Source: [Meteor Trajectories](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/render/Trajectories.java).

## Mining, farming and navigation pipelines

Meteor Nuker's bounded-target selection/render/tick structure was inspected in part, not fully audited. Its many shape, list, tool, packet-mine and rotation modes cannot be collapsed into a single “mine area” claim. Independent normal-action mining should maintain one active break target, check current hardness/tool/range, cancel on changed geometry and wait for the authoritative block update. A selection preview and material estimate can ship before bulk execution. Never infer removed blocks from a sent request.

Farmers, tunnel/highway builders, excavation, liquid filling and wither construction combine navigation, item selection, placement/breaking and resource policies. They need resumable task states and finite failure counts rather than one long uninterruptible loop. A native A* planner should use received collision geometry, admissible movement costs, a node/time budget, a generation token and replan on changed blocks. Unknown terrain remains an exploration boundary. A waypoint arrow and breadcrumbs are useful passive alternatives and are not pathfinding implementations. The delivered Waypoint Walk separately uses Horizon's bounded A* on loaded terrain with explicit activation and cancellation; it does not implement these multi-stage mining/farming pipelines. Meteor's InfinityMiner/Excavator depend on Baritone, so default module counts do not establish self-contained implementations. The register leaves the unreviewed task algorithms open.

| Phase, clip/teleport commands, Freecam | A visual/camera offset is not player teleportation, collision bypass or distant chunk loading. | Bounded detached camera and loaded-geometry inspection, local navigation markers. Label body versus camera positions and retain body simulation. |

| AutoSoup, commands/macros, AutoAccept, AutoReply | Depends on server plugin semantics and message formats; can perform unintended external actions. | Explicit server profile and allowlist, parsed typed commands, cancellation and bounded queues. These alternatives are design directions, not completed modules or proof that the original exploit modes are impossible on every server. Investigate an exact mode and pinned protocol before asserting compatibility. When an alternative is delivered, label the actual alternative instead of reusing a stronger reference name.
