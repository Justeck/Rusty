# Miscellaneous utilities, container transactions and integration boundaries

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

All 16 Meteor Misc module bodies, the three Swarm helper bodies, and the complete InventorySorter were read on 2026-11-04 at `e3a2e77967629d216e127b5ceecf71fb15f9d2e5`. AntiPacketKick's compression/NBT/bundle limits and exception branch, AutoReconnect's disconnect-screen mixin, and BetterBeacons' complete screen mixin were also traced. Notebot's song decoders/instrument detectors and the remaining chat/input/render mixins are not completely traced. These are focused behavior reviews, not reference runtime tests or native acceptance. Exact direct setting identifiers and pinned individual primary URLs remain in [the register](implementation-analysis-register.json).

Primary source directory: [Meteor Misc](https://github.com/MeteorDevelopment/meteor-client/tree/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/systems/modules/misc).

## Container sorting and transaction correctness

The complete [InventorySorter](https://github.com/MeteorDevelopment/meteor-client/blob/e3a2e77967629d216e127b5ceecf71fb15f9d2e5/src/main/java/meteordevelopment/meteorclient/utils/player/InventorySorter.java) plans stacking first, then selection-style sorting, and executes one planned move after its timer reaches the configured delay. Region classification excludes hotbar, peek views and unsupported inventories; player main and ordinary chest/shulker regions are distinct.

Stack grouping starts from same item **and components**, but simulated merged stacks are reconstructed from item/count only, losing components in the planning model. Sorting compares item registry key, then descending count, then descending damage value. These are observed implementation choices, not universal inventory quality. A native implementation should retain full immutable stack data in its model, define a stable configurable sort key and never treat same item ID as proof two stacks merge. Source plans are not recomputed after every acknowledgment, so a stale plan must not be transplanted into a server-driven native container.

The module clears an occupied cursor before sorting and drops it outside if no empty slot exists. Rusty should instead keep the user item safe and refuse/offer an explicit placement choice. The source's `stealDrop` branch performs an action only when `dropBackwards` is enabled; the other branch appears to do nothing. This is a static branch observation, not tested behavior. Every native transfer needs a menu ID plus generation, component-aware precondition, cursor precondition, one outstanding action, expected post-state and cancellation if the user changes any participating slot. Container close, world leave and another feature's action invalidate the plan.

## Notebot state machine and failure cases

The module's setup/tune/wait/check/play structure is a useful reusable automation pattern: actions decrement a local pending count, then received world state is re-read before proceeding. Exact-instrument assignment is greedy rather than a minimum-interaction bipartite matching. A native tuning planner can improve this by minimizing modulo-25 clicks subject to instrument/reach constraints, while still checking each ordinary action's result.

The two `polyphonic` branches in the pinned body both call the same playback method, so the setting does not visibly limit simultaneous notes here. Missing position during playback returns from the entire current chord. Random song selection recurses on unsupported files and calls random selection on an empty array if an empty directory is returned; filter the candidates once and choose iteratively. Async completion needs request/session generation even after cancellation because old callbacks can race a new load. The align-center UI writes player position directly; a normal movement task is the appropriate independent equivalent. Song decoder correctness, file bounds and mapping helpers require additional review before format-support claims.

## Integration failure cases found in the pinned source

- PacketLogger's cleanup sorts oldest first, accumulates sizes, then deletes entries **after** the running sum exceeds the total cap. That retains the old prefix and removes newer files, contrary to its oldest-removal comment. Independent retention should compute total first and remove oldest closed files until below budget. Never unlink the active writer.
- Notifier's totem predicate pairs friend entities with `ignore-others` and nonfriends with `ignore-friends`, opposite the setting labels. Native friend/self/other filters need a truth-table test. Range filtering occurs after the count increments; decide explicitly whether out-of-range pops count toward later summaries.
- BetterChat removes invalid regexes from a list while incrementing its index, which can skip the next adjacent invalid pattern. Preserve the user's list and compile a separate validated list with per-entry errors. Its content-only duplicate matching can merge messages from different senders; immutable sender/message IDs avoid that.
- SwarmConnection busy-loops while idle, has a single overwriteable pending message and no explicit interthread synchronization. Host does not reclaim a disconnected stored slot and does not close the fifty-first accepted connection in this body. Worker dispatch runs from its network thread. A bounded channel/event loop is required for any original integration.

These findings inform original designs and tests. They are not runtime reproductions, security advisories, or copied implementation code.
