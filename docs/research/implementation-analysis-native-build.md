# Native building adaptation and exact acceptance boundary

> Dated reference-mechanism research and design context. Current executable acceptance is recorded only in [Rusty validation](../VALIDATION.md).

The source analysis of AutoBuild, InstaBuild, InstantBunker, Scaffold, Tunneller and Excavator identifies useful common requirements: a bounded coordinate plan, real support/dependency checks, material ownership and a distinction between attempted and accepted placement. The delivered native adaptation is **Build Planner**: an original axis-aligned cuboid/shell preview plus an explicit one-block action. It is one of the42 bounded implemented modules, rather than a claim to implement every building reference. It is not continuous AutoBuild, template import, pathfinding construction, planner-controlled inventory refill, rotation spoofing, shelter replication or instant excavation. Separate Auto Refill replenishes an observed depleted hotbar slot; it does not select or acquire materials for a building plan.

Files: `mixins/rusty/build_plan.rs` (root-owned pure geometry/settings), `build_native.rs` (session-scoped state/display/action scheduling), `build_agent.rs` (private normal reachable-face aim facade), `build_actions.rs` (private ordinary remote block-use facade). The shared configuration, module/UI registration, life-cycle hooks and combined native build are integrated with the other action owners. No GPL or proprietary implementation was copied. These facades call the existing MIT-licensed pinned Horizon implementation rather than reconstructing packets.

## Native mechanisms actually reused

Reference SDK mechanism study: Horizon9aa4be3. Current Rusty targets6475f62; [fresh validation](../VALIDATION.md) records its own accepted executable. Reference analysis is not live-game acceptance.

* `crates/horizon-client/src/game/agent.rs::Game::aim_block`: normal eye/reach/collision-ray face selection, tries near/mid/center insets and requires actual hit block/face. The facade tries six received full-collision, nonreplaceable, non-block-entity neighboring supports. It does not extend reach or bypass an intervening entity at dispatch.
* `game/remote.rs::Game::remote_block_reacts`: native disposable-level interaction preflight rejects reactive support rather than accidentally opening a menu or toggling a block.
* `remote_can_place`: native BlockItem placement on `DryLevel`, including real shape/survival/entity obstruction. Owned write map, random source and captured events are discarded. Exact intended destination and exactly one changed cell are required, excluding redirected/multi-block results such as doors or beds.
* `remote_use_block(Main)`: the ordinary host block-use, local prediction, sound and item-consumption path. The facade respects playing-state handoff, current use delay, native interaction cancellation, selection synchronization, busy hands, survival building permission and existing mining. Native-mod-claimed and consumable block items are refused. No generic item or offhand fallback occurs.
* `remote.rs::Game::end_predictions`: a server sequence acknowledgment clears retained prediction entries and restores latest server-provided block state. The native state machine waits until the target prediction entry is absent and compares the target state with the exact expected native placement result. The return from a use call alone is never counted as accepted.

Passive preview never calls these mutating/private placement facades. The explicit Place Next action's normal `with_level` preflight also flushes previously queued host effects after its disposable simulation; therefore the entire explicit action is not advertised as a read-only probe. The ordinary SDK dispatch can predict the requested change immediately; the visible matching-material count is an observation, distinct from the accepted-action counter.

## Original scheduling and limits

Set Origin uses the adjacent cell outside the currently hit received block face and binds it to the navigation subsystem's verified server/local-save identity and dimension. Each dimension is1..16; checked coordinates and maximum4096cells are validated before allocation. Hollow side walls, independent floor/roof flags and solid fill share a deterministic bottom-up original plan. Matching means **same material name as the currently held block**, not exact orientation/properties or proof that this tool placed the block.

At most every250ms the adapter classifies all bounded cells as matching material, missing/replaceable, occupied or unknown. It sorts by player distance and emits at most128unit-cell wireframes/1536depth-tested lines. Height/chunk absence stays unknown; no world data is requested or invented. An anchored preview performs this bounded received-cell classification; it does not request placement/mining or run the private native placement simulation until an explicit Place Next action.

Place Next captures selected slot and exact item/components only after checking the available wire patch is at most16KiB. The queued action waits for the host's normal playing-state handoff; any manual input once playing cancels it permanently. It checks up to32bottom-up nearest missing candidates for reachable support, aims normally, waits for a later client tick, then revalidates exact item/count/selection, view/target, context and cooldown before dispatch. It never moves inventory or holds a key/mouse button. Existing assistance, fishing/totem, inventory and navigation ownership blocks a new request. Changed settings, unavailable world, death/menu/focus/freecam, remote correction or replacement context cancel pending work; no automatic retry/replay follows a timeout or manual release. Post-dispatch normal server effects cannot be undone by cancelling the local observer.

The total request lifetime is5s, including queue/aim/acknowledgment. The accepted counter advances only on settled matching native state. Missing acknowledgment, rejected result or unloaded target ends with an explicit result and requires another user action. World/server transition or disabling clears transient anchor/geometry/action state. Source fields are diagnostic observations. The official Java fixture now supplies separate authoritative block and item readbacks for the explicit placement; that acceptance remains limited to the tested operation and conditions.

## Verification gates and remaining building scope

Rusty's fresh builder fixture must exercise Set Origin/Place Next through the actual menu, preserve world/inventory during passive preview, confirm one ordinary Survival placement and no automatic second placement, cancel on manual input, enforce the4096-cell/128-outline bounds, and clear state on disable. The separate owned Java fixture supplies authoritative block/item readbacks. Only [current validation](../VALIDATION.md) and its newly generated receipts establish the results.

Further discriminating cases include actors entering the target between aim and dispatch, reactive support, hook cancellation, claimed/large-component items, multi-block placement, occupied targets, permission failures, delayed acknowledgment, focus loss, corrections, session/dimension changes and resource/material changes. No arbitrary-plugin guarantee, continuous AutoBuild, schematic interchange or reference parity is claimed.
